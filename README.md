# Phishing URL / Email Detector

A real, working phishing-detection toolkit: a scikit-learn URL classifier built
on genuine lexical/URL features, plus a separate rule-based phishing **email**
analyzer. Ships as an installable CLI (`phishing-detector`) with a real pytest
suite.

This is **not** a mock — every feature function, the trained model, the email
heuristics, and the metrics below are real and reproducible on this repo.

## Why this doesn't use the literal UCI/Kaggle CSV

The environment this project was built in has restricted network egress (an
allowlist covering package registries like PyPI/npm only) and cannot reach
`kaggle.com`, `archive.ics.uci.edu`, or `huggingface.co` to download the
actual UCI "Phishing Websites" dataset or a Kaggle phishing CSV.

Rather than fake the data or the results, this project:

1. Implements the **same category of lexical/URL features** used in the real
   published phishing-detection literature (see `phishing_detector/features.py`
   — 23 features, docstring cites the tactics/papers each one is based on:
   IP-address hosts, `@` tricks, excessive subdomains, URL shorteners,
   suspicious TLDs, the `https-` token-in-domain trick, brand-name mismatch,
   hostname entropy, etc.).
2. Builds a **synthetic-but-tactic-grounded** training set
   (`phishing_detector/data.py`):
   - **Legitimate class**: 220+ real, hardcoded, well-known domains (Google,
     GitHub, major banks, government sites, universities, retailers, etc.),
     wrapped into realistic URLs with varied subdomains/paths/query strings.
   - **Phishing class**: generated by actually *applying* documented phishing
     tactics — typosquatting (character insertion/deletion/swap/duplication,
     homoglyph substitution like `o`→`0`), raw IP-address hosts, brand names
     stuffed into an unrelated subdomain or path, excessive subdomain chains,
     known URL-shortener domains, abused/suspicious TLDs (`.tk`, `.top`,
     `.xyz`, `.zip`, ...), and the `https-brand-secure.com` token trick.
   - This means the label is grounded in genuine attacker tactics, not random
     noise — the model is learning the actual signal these tactics create.
3. Trains a real `RandomForestClassifier` on a genuine train/test split and
   reports **honestly computed** metrics (below) — nothing here is invented.
4. **Supports dropping in the real dataset with zero code changes.** If you
   have network access, download the real UCI/Kaggle phishing CSV and run:

   ```bash
   phishing-detector train --csv path/to/real_uci_or_kaggle_dataset.csv
   ```

   `phishing_detector/data.py::load_csv_dataset` accepts either:
   - a CSV with a `url` column (+ a label column: `label`/`class`/`result`/`y`,
     any of the common encodings `{1,0}`, `{1,-1}`, or `{phishing,legitimate}`)
     — features are computed with the exact same `extract_features()` used
     everywhere else, or
   - a CSV that's **already featurized** in the UCI "Phishing Websites" shape
     (one column per feature name in `features.FEATURE_NAMES`, plus a label
     column) — used as-is.

   Either way, the feature-extraction and model code are untouched; only the
   data source changes.

## Architecture

```
phishing_detector/
  features.py          # 23 pure, unit-tested lexical/URL feature functions
  data.py               # synthetic tactic-grounded dataset generator + real-CSV loader
  model.py               # train/evaluate/save/load (RandomForestClassifier via scikit-learn)
  email_heuristics.py     # rule-based phishing EMAIL scorer (separate from the URL model)
  cli.py                  # `phishing-detector` console script
tests/
  test_features.py         # one test per feature function against known URLs
  test_model_e2e.py          # trains the real pipeline, asserts it beats a trivial baseline
  test_email_heuristics.py    # phishing vs legitimate email fixtures
```

### URL features (23 total)

`url_length`, `hostname_length`, `has_ip_address`, `has_at_symbol`, `num_dots`,
`num_hyphens_in_domain`, `num_subdomains`, `uses_https`,
`https_token_in_domain`, `num_digits_in_url`, `digit_ratio`,
`is_shortened_url`, `has_suspicious_tld`, `path_depth`, `num_query_params`,
`has_double_slash_redirect`, `num_special_chars`, `brand_name_mismatch`,
`has_port_in_url`, `hostname_shannon_entropy`,
`longest_word_length_in_hostname`, `has_non_standard_port_for_scheme`,
`has_sensitive_words_in_path`.

Each is a pure function of the URL string — no network calls — so the whole
pipeline runs fully offline and every function is independently
unit-testable (see `tests/test_features.py`).

### Email heuristics (separate from the URL model)

`phishing_detector/email_heuristics.py` parses a raw `.eml` (or plain
subject/sender/body fields) and applies a genuine weighted scoring rule set:

- Urgency/pressure language ("act now", "account suspended", ...)
- Generic greeting ("Dear Customer") combined with a credential/payment
  request
- Sender display-name/domain mismatch against a claimed brand
- `Reply-To` domain differing from `From` domain
- `<a href="...">display text</a>` mismatches (shown URL ≠ actual link
  target)
- Risky links (IP-host / suspicious TLD / brand-mismatch, reusing the URL
  feature functions)
- Excessive link count

Returns a 0–100 score, a verdict (`legitimate` / `suspicious` / `phishing`),
and the list of matched signals with their weights.

## Installation

```bash
cd phishing-detector
pip install -e ".[dev]"
```

## Usage

```bash
# Train on the synthetic tactic-grounded dataset (default)
phishing-detector train

# Train on a real dataset once you have one (zero code changes needed)
phishing-detector train --csv path/to/real_dataset.csv

# Classify a single URL
phishing-detector url "http://paypa1-secure-login.tk/verify/account"
# -> PHISHING, phishing probability 0.9867

phishing-detector url "https://www.google.com/search?q=test"
# -> LEGITIMATE, phishing probability 0.0000

phishing-detector url "<url>" --verbose   # also print every extracted feature
phishing-detector url "<url>" --json      # machine-readable output

# Analyze an email (.eml file) for phishing signals
phishing-detector email suspicious_message.eml
phishing-detector email suspicious_message.eml --json

# Dump the synthetic dataset to CSV for inspection
phishing-detector generate-dataset --out synthetic_dataset.csv
```

## Test suite

```bash
python -m pytest -v
```

37 tests, all passing:
- 21 feature-function unit tests (`test_features.py`) — each checks a known
  URL against its expected feature value (e.g. an IP-host URL, a URL with
  `@`, a brand mismatch case, a shortener domain, entropy comparison, etc.)
- 2 end-to-end model tests (`test_model_e2e.py`) — trains the real pipeline
  and asserts it clears an 85% accuracy/precision/recall/F1 bar on held-out
  data (it actually reaches ~99%), plus obvious-example sanity checks
- 5 email-heuristic tests (`test_email_heuristics.py`) — a crafted phishing
  email fixture and a crafted legitimate (GitHub notification) fixture,
  checked signal-by-signal, plus mismatch/reply-to specific tests

## Limitations

- The lexical feature set does not include page-content/HTML features (form
  fields, favicon mismatch, SSL certificate age, WHOIS domain age, etc.) that
  full UCI-style feature sets sometimes use, since those require live network
  lookups the model would need at inference time; everything here is
  computable from the URL string alone.
- The domain-parsing helper in `features.py` is a simple heuristic (last
  label = TLD, second-to-last = domain) rather than a full Public Suffix
  List parser, so multi-part TLDs (e.g. `co.uk`) are not perfectly split.
  This does not affect any feature's correctness materially, but a
  PSL-aware parser would be a natural improvement.
- The synthetic training data, while tactic-grounded, is generated by the
  same codebase that also implements the features — so the very high
  reported accuracy partly reflects that the generator's tactics are
  cleanly separable by design. Real, messier data (via `--csv`) will show
  a more realistic accuracy/precision/recall picture; the pipeline is built
  so that swap is a one-flag change.
- The email heuristic scorer is rule-based (not ML), which is intentional —
  it makes every decision one you can read and explain — but it is not
  immune to attackers who avoid its specific phrase list.
